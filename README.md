# depgraph

Инструмент визуализации графа зависимостей для менеджера пакетов NuGet (.NET).
Практическая работа «Конфигурационное управление», вариант 12.

## 1. Общее описание

Проект выполняется по этапам. Сейчас готов **этап 4**: программа читает настройки из
INI-файла, строит **полный граф зависимостей** пакета (прямые и транзитивные зависимости)
обходом в ширину (BFS) без рекурсии и выводит либо сам граф, либо **порядок загрузки**
пакетов. Умеет:

- работать с настоящим репозиторием NuGet (nuget.org) по HTTP;
- работать в тестовом режиме с графом из простого текстового файла;
- пропускать пакеты, в имени которых есть заданная подстрока;
- корректно обрабатывать циклические зависимости;
- выводить порядок загрузки: сначала зависимости, потом пакеты, которые от них зависят
  (режим `output_mode = load_order`).

Визуализация будет добавлена на этапе 5.
Готовые менеджеры пакетов (`dotnet`, `nuget`) и сторонние библиотеки не используются.
Всё делается средствами стандартной библиотеки Java 21: `java.net.http` для запросов,
`javax.xml` для разбора описания пакета. Для тестов нужен JUnit 5.

## 2. Функции и настройки

Конфигурация хранится в INI-файле, секция `[depgraph]`:

| Ключ | Обязателен | Описание |
|---|---|---|
| `package_name` | да | Имя анализируемого пакета. Идентификатор NuGet (буквы, цифры, `.`, `_`, `-`); в тестовом режиме только большие латинские буквы `A-Z` |
| `repository` | да | URL индекса репозитория (`http://` или `https://`) или, при `test_mode = true`, путь к файлу тестового репозитория |
| `test_mode` | да | Режим работы с тестовым репозиторием: `true`/`false` |
| `package_version` | да | Версия пакета: `13.0.3`, `1.2.3.4`, `1.0.0-beta.1` (в тестовом режиме не используется) |
| `filter_substring` | нет | Пакеты, в имени которых есть эта подстрока, не учитываются при анализе (с учётом регистра) |
| `output_mode` | нет | Что печатать: `graph` (граф, по умолчанию) или `load_order` (порядок загрузки) |

Синтаксис INI: секции `[имя]`, пары `ключ = значение`, комментарии отдельной
строкой (`;` или `#`). Ключи не зависят от регистра, повторы запрещены.

Аргумент командной строки: путь к INI-файлу (по умолчанию `config.ini` в текущей папке).

### Как строится граф

1. Корневой пакет ставится в очередь.
2. Пока очередь не пуста: берём пакет из начала очереди, узнаём его прямые зависимости,
   добавляем в граф стрелки «пакет зависит от X» и ставим в **конец** очереди те
   зависимости, которых ещё не видели. Так пакеты обходятся по уровням (BFS).
3. Пакеты с подстрокой из `filter_substring` в граф не попадают, их зависимости не
   обходятся. Пустая подстрока ничего не исключает.
4. **Циклы.** Каждый пакет ставится в очередь только один раз (множество уже виденных
   пакетов), поэтому обход всегда заканчивается. Стрелка на уже виденный пакет в граф
   добавляется, и цикл виден в результате. Связи, лежащие на циклах, печатаются отдельной
   строкой.

### Порядок загрузки (этап 4, `output_mode = load_order`)

Порядок загрузки это такой порядок пакетов, в котором каждый пакет стоит **после** всех
пакетов, от которых он зависит. Корневой пакет всегда последний. Считается топологической
сортировкой графа (алгоритм Кана, без рекурсии):

1. Для каждого пакета считаем, сколько его зависимостей ещё не загружено.
2. Пакеты с нулевым счётчиком (у них нет зависимостей или все уже загружены) готовы.
   Они идут в очередь в порядке обхода BFS.
3. Берём пакет из очереди, добавляем в итоговый список, а у пакетов, которые от него
   зависят, уменьшаем счётчик на единицу. У кого счётчик стал нулевым, ставим в очередь.
4. Когда очередь опустела, порядок готов.

Подходящих порядков обычно много (например, `B` и `C` можно загружать в любом порядке);
программа выдаёт один из них, предсказуемый благодаря обходу BFS.

**Циклы.** Если пакеты зависят друг от друга по кругу, строгий порядок невозможен: каждый
ждёт другого. Программа не учитывает связи, лежащие на цикле, поэтому остальные пакеты
по-прежнему стоят после своих зависимостей, а пакеты цикла получают условный порядок
и помечаются «(в цикле)» с предупреждением.

### Откуда берутся зависимости

**Настоящий репозиторий (`test_mode = false`).**

1. Скачивается индекс (`repository`), например `https://api.nuget.org/v3/index.json`.
   В нём находится сервис `PackageBaseAddress/3.0.0`: адрес хранилища пакетов.
2. Для пакета скачивается описание `{адрес}/{имя}/{версия}/{имя}.nuspec` (XML), из него
   берутся элементы `dependency`.
3. Версия зависимости задана диапазоном (`[13.0.1, )`, `4.3.0`). Как и NuGet, программа
   выбирает самую низкую подходящую версию, то есть нижнюю границу диапазона. Если нижней
   границы нет, берётся самая первая версия пакета из списка версий.

В `.nuspec` зависимости разложены по группам для разных версий платформы .NET. Программа
объединяет все группы.

**Тестовый репозиторий (`test_mode = true`).** `repository` это путь к текстовому файлу.
Одна строка описывает один пакет: `A: B C` значит «A зависит от B и C».
Имена состоят из больших латинских букв. Пустые строки и строки с `#` в начале
пропускаются. Пакет, который нигде не стоит слева от двоеточия, не имеет зависимостей.
Корневой пакет обязан быть описан в файле.

```
# Ромб: от пакета D зависят и B, и C
A: B C
B: D
C: D
D:
```

### Обработка ошибок

Сообщение выводится в stderr, код завершения 1.

- Настройки: файл не найден или это каталог, не читается или не UTF-8, нарушен синтаксис
  INI (с номером строки), неизвестный или пропущенный ключ, пустое значение, неверные
  `test_mode`, имя пакета, URL, путь к тестовому репозиторию, версия; корневой пакет
  содержит подстроку фильтра.
- Получение данных: нет связи с сервером или превышено время ожидания (15 секунд),
  индекс, пакет или версия не найдены (HTTP 404), другой код ответа сервера, в индексе нет
  нужного сервиса, описание пакета не разобрать.
- Тестовый репозиторий: файл не читается, неверная строка (с номером), имя не из больших
  латинских букв, пакет описан дважды, корневой пакет не найден.

## 3. Сборка и тесты

Запуск (сборка и старт): `run.bat` (Windows) или `./run.sh` (Linux/macOS; без права на
выполнение: `sh run.sh`). Первым аргументом можно передать путь к INI-файлу.

Демонстрационные скрипты есть в двух вариантах, `.bat` и `.sh`: `scripts/demo_errors`
(все примеры с ошибками), `scripts/demo_test_repo` (тестовый репозиторий, граф) и
`scripts/demo_load_order` (тестовый репозиторий, порядок загрузки).

Ручная сборка:

    javac -encoding UTF-8 -d out src/*.java

Тесты (JUnit 5, `junit-platform-console-standalone.jar` положить рядом).
Интернет для тестов не нужен: вместо nuget.org поднимается локальный сервер.

    javac -encoding UTF-8 -d out -cp junit-platform-console-standalone.jar src/*.java tests/*.java
    java -jar junit-platform-console-standalone.jar -cp out --scan-classpath

В IntelliJ IDEA: папка `src` помечена как Sources, `tests` как Test Sources.

## 4. Примеры использования

### Тестовый режим (`scripts\demo_test_repo.bat` запускает все примеры)

Ромб, без циклов (`examples\test_diamond.ini`):

    > run.bat examples\test_diamond.ini
    Граф зависимостей пакета A (пакетов: 4, связей: 4)
      A -> B, C
      B -> D
      C -> D
      D -> (нет зависимостей)
    Циклических зависимостей нет.

Цикл A -> B -> C -> A (`examples\test_cycle.ini`):

    > run.bat examples\test_cycle.ini
    Граф зависимостей пакета A (пакетов: 3, связей: 3)
      A -> B
      B -> C
      C -> A
    Циклические зависимости (связи, которые лежат на цикле): A -> B, B -> C, C -> A

Фильтр `B` (`examples\test_filter.ini`):

    > run.bat examples\test_filter.ini
    Граф зависимостей пакета A (пакетов: 3, связей: 2)
    Фильтр: пакеты, в имени которых есть 'B', пропущены
      A -> C
      C -> D
      D -> (нет зависимостей)
    Циклических зависимостей нет.

Другие примеры: `test_complex.ini` (несколько веток и цикл), `test_self.ini` (пакет
зависит сам от себя), `test_from_c.ini` (граф от другого корня).

### Порядок загрузки на тестовом репозитории (`scripts\demo_load_order.bat` запускает все примеры)

Ромб (`examples\order_diamond.ini`): `D` нужен и `B`, и `C`, поэтому он первый, корень `A` последний.

    > run.bat examples\order_diamond.ini
    Порядок загрузки пакета A (сначала зависимости, потом сам пакет). Пакетов: 4
       1. D
       2. B
       3. C
       4. A
    Циклических зависимостей нет, порядок строгий.

Цепочка `A -> B -> C -> D` (`examples\order_chain.ini`): загрузка идёт с конца, `D`, `C`, `B`, `A`.

Сложный граф с циклом `B -> E -> B` (`examples\order_complex.ini`):

    > run.bat examples\order_complex.ini
    Порядок загрузки пакета A (сначала зависимости, потом сам пакет). Пакетов: 7
       1. D
       2. F
       3. G
       4. B (в цикле)
       5. E (в цикле)
       6. C
       7. A
    Внимание: найдены циклические зависимости. Порядок пакетов, помеченных «в цикле», определить нельзя, он показан условно.

Цикл `A -> B -> C -> A` (`examples\order_cycle.ini`): все три пакета помечены «в цикле».
Фильтр `B` (`examples\order_filter.ini`): порядок `D`, `C`, `A`, пакета `B` в нём нет.
Пакет, зависящий сам от себя (`examples\order_self.ini`): `B`, затем `A (в цикле)`.

### Настоящий репозиторий

    > run.bat examples\logging.ini
    Граф зависимостей пакета Microsoft.Extensions.Logging 8.0.0 (пакетов: 88, связей: 478)
      Microsoft.Extensions.Logging -> Microsoft.Bcl.AsyncInterfaces, Microsoft.Extensions.DependencyInjection, ...
      ...

Граф получается большим, потому что объединяются зависимости для всех версий платформы
.NET, а построение занимает около 15 секунд (сотни запросов к серверу). Циклы в таком
графе возникают из-за этого объединения.

### Ошибки (`scripts\demo_errors.bat` запускает все примеры из `examples\errors`)

    > run.bat examples\errors\test_root_missing.ini
    Ошибка получения данных: пакет Z не найден в тестовом репозитории

    > run.bat examples\errors\test_bad_format.ini
    Ошибка получения данных: тестовый репозиторий, строка 3: ожидается запись вида 'A: B C'

    > run.bat examples\errors\package_not_found.ini
    Ошибка получения данных: пакет No.Such.Package.Xyz123 версии 1.0.0 не найден в репозитории

    > run.bat examples\errors\bad_url.ini
    Ошибка конфигурации: repository: нужен адрес вида https://..., а не 'ftp://example.com'

    > run.bat examples\errors\bad_output_mode.ini

## 5. Сравнение порядка загрузки с настоящим менеджером NuGet (этап 4)

### Как сравнивали

Настоящий менеджер NuGet (`nuget.exe` 8.0.0, официальный, от Microsoft) запускался **вручную,
только для проверки**. В программе и в репозитории его нет. Команда для каждого пакета:

    nuget install <пакет> -Version <версия> -Framework <платформа> -Source https://api.nuget.org/v3/index.json

Менеджер по умолчанию берёт самую низкую подходящую версию зависимостей (как и наша программа).
Порядок загрузки это порядок строк `Added package ...` в его подробном выводе (`-Verbosity detailed`).
Нашу программу запускали с `output_mode = load_order` (`examples\nuget_order_logging.ini` и аналогичные).

### Результаты

| Пакет | Платформа | Пакетов у программы | Пакетов у NuGet | Есть только у программы | Только у NuGet | Версии различаются | Порядок общих пакетов |
|---|---|---|---|---|---|---|---|
| AutoMapper 12.0.1 | netstandard2.1 | 78 | 2 | 76 | 0 | 0 | совпадает |
| Microsoft.Extensions.Logging 8.0.0 | net8.0 | 88 | 6 | 82 | 0 | 0 | совпадает |
| Microsoft.Extensions.Logging 8.0.0 | netstandard2.0 | 88 (5 в цикле) | 14 | 74 | 0 | 1 | различается |
| Newtonsoft.Json 13.0.3 | net6.0 | 86 | 1 | 85 | 0 | 0 | совпадает |
| Newtonsoft.Json 13.0.3 | netstandard1.3 | 86 | 74 | 12 | 0 | 0 | различается |

Во всех случаях корневой пакет стоит последним и у программы, и у NuGet, а любой пакет
загружается после своих зависимостей. Все пакеты, которые ставит NuGet, есть и в результате
программы (колонка «Только у NuGet» везде нулевая).

Пример, где результат полностью совпал по порядку: `Microsoft.Extensions.Logging 8.0.0` на `net8.0`.
NuGet ставит `Microsoft.Extensions.DependencyInjection.Abstractions`, `Microsoft.Extensions.DependencyInjection`,
`Microsoft.Extensions.Logging.Abstractions`, `Microsoft.Extensions.Primitives`, `Microsoft.Extensions.Options`,
`Microsoft.Extensions.Logging`. Эти шесть пакетов идут в том же порядке и в результате программы.

### Почему есть расхождения

1. **Платформы объединяются (главная причина).** В описании пакета (`.nuspec`) зависимости разложены
   по группам для разных версий платформы .NET. NuGet берёт **одну** группу, подходящую выбранной платформе.
   В задании выбора платформы нет, поэтому программа **объединяет все группы**, причём на каждом уровне
   цепочки. Отсюда лишние пакеты. Пример: у `AutoMapper 12.0.1` одна зависимость `Microsoft.CSharp 4.7.0`,
   но у `Microsoft.CSharp` для старых платформ в описании сотни зависимостей, поэтому в графе программы 78 пакетов,
   а для `netstandard2.1` NuGet ставит только 2.
2. **Часть пакетов уже входит в платформу.** Для современных платформ (`net6.0`, `net8.0`) многие библиотеки
   `System.*` входят в саму платформу и не скачиваются. Поэтому `Newtonsoft.Json` на `net6.0` ставится как один пакет.
3. **Версии.** Программа выбирает версию по первому найденному пути (нижняя граница диапазона), а NuGet выбирает
   версию внутри одной платформы. Единственное расхождение: `System.Numerics.Vectors`, у нас 4.5.0, у NuGet 4.4.0.
   Исключающая граница диапазона `(1.0, )` программа считает включающей.
4. **Порядок.** Подходящих порядков много, а они отличаются выбором «кого загружать первым» среди независимых
   пакетов. NuGet выбирает их своим алгоритмом, программа идёт по очереди обхода BFS. Оба порядка верны: зависимости
   раньше зависимых. Если зависимости образуют цепочку (один допустимый порядок), результаты совпадают.
5. **Циклы.** Для `Microsoft.Extensions.Logging` программа нашла 5 пакетов в цикле (`System.Memory`, `System.Numerics.Vectors`,
   `NETStandard.Library` и другие). Для одной платформы цикла нет, он появляется только из-за объединения платформ.
   NuGet для одной платформы циклов не видит.
6. **Пакеты других платформ и систем.** В случае `Newtonsoft.Json` на `netstandard1.3` у программы 12 лишних пакетов:
   `System.Security.Cryptography.Cng`, `.Csp`, `.OpenSsl`, `System.Runtime.WindowsRuntime`,
   `System.Collections.NonGeneric`, `System.Collections.Specialized` и другие. Они входят в группы других платформ
   в описаниях пакетов `System.*`, а `netstandard1.3` использует меньшую группу.

### Вывод

Программа даёт **надмножество** того, что ставит настоящий менеджер: расхождения возникают из-за того,
что менеджер решает задачу для одной платформы, а программа по условию задания собирает зависимости
всех платформ сразу. На порядок загрузки это не влияет: в обоих случаях сначала идут зависимости,
а корневой пакет последний.
